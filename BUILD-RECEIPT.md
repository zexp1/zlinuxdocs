## 5. PDF/A — the honest position, stated in five places

**PDF/A conformance is NOT claimed anywhere.** `convert --pdfa` exists, and its
help says exactly what it does and does not guarantee:

ABOUT PDF/A: --pdfa asks LibreOffice to export in a PDF/A archival flavour.
It does NOT prove the result conforms. Nothing in this program can verify
PDF/A conformance - that needs a dedicated validator such as veraPDF. So do

## 7. Honest FLAGs and PENDING items

### FLAG 1 — `python3-lxml` is a hard Depends. The R3 vendoring policy could not be met in full.

R3 said to vendor python-docx and hard-depend only on `python3` and
`poppler-utils`. python-docx **cannot** run without `lxml`:

```
$ grep -i '^Requires-Dist' python_docx-1.1.2.dist-info/METADATA
Requires-Dist: lxml >=3.1.0
Requires-Dist: typing-extensions >=4.9.0
```

`lxml` is a compiled C extension against libxml2/libxslt. It cannot go into an
`Architecture: all` package without either shipping per-architecture binaries
or making the package arch-specific. Both are worse than one extra `Depends`
line on a ~1.5 MB package that is in every Debian and Ubuntu release.

So the shipped policy is:

```
Depends: python3 (>= 3.10), python3-lxml, poppler-utils
Recommends: qpdf, libreoffice-writer
```

`typing_extensions` (the other python-docx requirement) *is* pure Python and
**is** vendored, so it adds no dependency.

This is recorded here rather than quietly resolved, because it contradicts the
sealed R3 verdict. The verb-availability matrix in the README shows exactly
which verbs `python3-lxml` gates (`inspect` and `fix-headings`; `markers` needs
nothing beyond Python, `validate` and `profile` are unaffected).

Also deviating from R3, deliberately: `libreoffice-writer` is Recommended
rather than `libreoffice-writer-core`, because on Ubuntu 24.04
`libreoffice-writer-core` is not an installable package name — the message a
user is given must name a package that exists.

### FLAG 2 — vendoring was done ONLINE, from PyPI wheels, at build-prep time.

The network was available, so the vendored trees are genuine upstream releases,
unpacked from official wheels and committed to this repo:

| vendored | version | source | licence shipped |
|---|---|---|---|
| `vendor/docx/` | python-docx 1.1.2 | `python_docx-1.1.2-py3-none-any.whl` | `vendor/docx/LICENSE` (MIT) |
| `vendor/yaml/` | PyYAML 6.0.2 | `PyYAML-6.0.2-cp312-…whl`, **pure-Python portion only** | `vendor/yaml/LICENSE` (MIT) |
| `vendor/pypdf/` | pypdf 5.1.0 | `pypdf-5.1.0-py3-none-any.whl` | `vendor/pypdf/LICENSE` (BSD-3) |
| `vendor/typing_extensions.py` | 4.12.2 | `typing_extensions-4.12.2-py3-none-any.whl` | `vendor/typing_extensions.LICENSE` (PSF-2.0) |

The libyaml C accelerator (`_yaml`, `PyYAML.libs`) was **not** taken — only the
pure-Python `yaml/` package, which falls back cleanly (`__with_libyaml__ =
False`). Nothing was "borrowed from site-packages and called vendored": the
system `python3-docx` is 1.1.0 and the vendored copy is 1.1.2, which is itself
proof the two are unrelated. `debian/copyright` carries the aggregated notice.

At **runtime** nothing is fetched, ever. The entry script prepends
`/usr/share/zlinuxdocs/vendor` to `sys.path` once, with no
`try/except ImportError` fallback to a system package.

### FLAG 3 — proved on one machine and one distribution.

Everything above was observed on Ubuntu 24.04 (kernel 6.8.0, Python 3.12.3,
amd64). `Architecture: all` and the pure-Python code mean it *should* install
on any Debian-family machine and any CPU, but that has not been observed on a
second machine, on arm64, or on WSL. Treat "works on Debian 12 / arm64 / WSL"
